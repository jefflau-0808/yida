# 衣搭（Yida）MVP 技术方案

- 版本：v1.0
- 日期：2026-09-10
- 状态：已确认技术方向，待实施；本文件不代表功能已开发完成
- 仓库：jefflau-0808/yida
- 关联文档：[MVP 产品设计](./MVP-PRD.md)、[现有 Demo](../demo/README.md)
- 本次范围：编写技术方案，不修改 Demo、不接入付费服务、不部署新版本。

## 1. 目标与范围

实现中文、手机优先的响应式 Web/PWA，围绕以下流程交付：

拍摄／选择上衣 → 识别并确认标签 → 自动收录衣柜 → 推荐裤子与鞋子 → 生成整套搭配示意图 → 收藏与再次选用。

不要求提前录入全部衣服。衣柜在使用中逐步积累；推荐优先使用已录入的合适单品，未匹配部分给出款式、颜色、版型建议，帮助用户寻找自己的相似衣物。

### 最新需求与原产品文档的衔接

用户在 Demo 体验后进一步确认：正式 MVP 应包含“上衣＋裤子＋鞋子”的整套 AI 搭配示意图，不仅是两张单品图片。
因此本方案在图片范围上补充并替代原 PRD 第 4.4 节“不要求包含上衣、已有单品可不生成图片”的早期设计：
- 一套推荐对应一张整套衣物组合示意图。
- 即使裤子、鞋子已在衣柜中，也支持生成整套示意图。
- 同时保留真实单品卡片与“衣柜已有／衣柜有相似款／AI 参考款”标识。
- 不做用户本人虚拟试衣，不承诺真实上身效果或尺寸适配。

首版不包含 Electron 桌面客户端、原生手机应用、商品购买、支付、社交、实时天气、身材识别及自训练模型。
账号和跨设备云衣柜属于后续范围，未经确认不自动加入首版。

## 2. 当前 Demo 与正式 MVP 的区别

| 项目 | 当前 Demo | 正式 MVP 目标 |
| --- | --- | --- |
| 界面 | 原生 HTML、CSS、JavaScript | React、TypeScript、Next.js |
| 衣物识别 | 预设标签，用户手改 | 真实视觉识别，可手动校正 |
| 搭配推荐 | 两套预设数据循环 | 结构化 AI 推荐＋已有单品匹配 |
| 搭配图片 | 示例商品素材 | 真实生成整套衣物组合示意图 |
| 衣柜存储 | localStorage | IndexedDB，图片使用 Blob |
| PWA | 尚未实现完整能力 | 安装支持、离线查看已保存内容 |
| 后端 | 无业务后端 | 安全调用 AI、管理生成任务与费用 |

保留 demo/ 作为流程原型，不原地覆盖成正式应用。正式实现建议放在 web/，复用已验证的交互与业务规则思路，不照搬直接拼接 HTML 的实现。
Demo 中第三方图片不直接进入正式产品；替换为用户授权照片、明确许可素材或真实生成结果。

## 3. 技术选型与理由

| 层级 | 选型 | 原因与限制 |
| --- | --- | --- |
| UI | React + TypeScript | 组件化维护衣柜、表单和异步状态，静态类型减少接口错配 |
| 应用框架 | Next.js App Router | 页面和轻量服务端接口放在同一项目，不另起独立业务后端 |
| 样式 | CSS Modules + CSS 变量 | 延续 Demo 视觉，统一间距、颜色和断点，首版不引入额外样式框架 |
| 本地数据 | IndexedDB，封装独立存储层 | 异步保存标签、照片 Blob、收藏及任务引用 |
| AI 服务 | 可替换的视觉／文本／图像适配器 | 不把页面与某一家供应商 SDK 绑定 |
| 后台任务 | 优先供应商原生异步任务；应用侧持久任务记录 | 支持刷新恢复、幂等提交和过期清理 |
| 校验 | 共享运行时 Schema，例如 Zod | 服务端与客户端同时校验，TypeScript 不替代运行时验证 |
| 测试 | Vitest + React Testing Library + Playwright | 分别覆盖业务规则、组件行为和真实浏览器流程 |
| 版本管理 | GitHub yida，锁文件与 CI | 每次变更可追踪，测试通过后交付 |

采用支持所选 Next.js 版本的 Node.js LTS 运行环境。初始化时核对兼容性和依赖安全策略，在 package.json、运行时版本文件和锁文件中锁定实际版本；本方案不把浮动 latest 当作可复现配置。

Next.js 可通过 Route Handlers 提供应用接口，但不是可靠长任务队列的替代品。[官方后端接口指南](https://nextjs.org/docs/app/guides/backend-for-frontend)
IndexedDB 支持结构化数据和文件／Blob，适合本地衣柜图片。[MDN IndexedDB 文档](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)

### 为什么暂不使用 Electron

Electron 用于桌面客户端，而首版核心设备是手机浏览器。当前不增加桌面安装包、自动更新和系统权限维护。
未来若需要专门的桌面衣柜管理工具，再独立评估；不能用 Electron 替代移动端方案或 AI 后端。

## 4. 系统边界

浏览器负责：
- 拍照／文件选择、图片压缩、标签确认、衣柜与收藏。
- 本地候选筛选与重复提示、展示服务端返回的推荐。
- 任务轮询、状态恢复、错误重试与离线提示。

Next.js 服务端负责：
- 请求校验、匿名访问会话、限流、额度、幂等控制。
- 调用真实视觉、文本和图像服务，校验模型输出。
- 维护最少量的持久任务元数据和短期图片结果，不默认建设云衣柜。
- 隔离密钥，不向客户端暴露供应商凭据。

供应商适配层负责：
- analyzeGarment：识别照片为结构化标签。
- recommendOutfit：根据已确认标签、场景和候选生成建议。
- createOutfitImage／getImageJob：创建并查询整套图任务。
- normalizeError：把供应商错误映射为可理解的应用错误。

mock 和 real 两种实现遵守同一接口。mock 只用于开发、测试或用户主动选择的演示模式；真实服务失败时不得偷偷切换成模拟成功结果。

## 5. 核心业务流程

### 5.1 上传、识别与自动收录

1. 选择 JPEG、PNG 或 WebP，原文件不超过 10 MB；无效格式、损坏文件、超限像素应拒绝。
2. 客户端校正方向、压缩最长边至 1280px 并重新编码，移除 EXIF。压缩后的上传目标不超过 2 MB；超限继续压缩或提示换图。
3. 选图本身不发送 AI 请求。用户阅读用途说明并点击“识别衣物”后才发送。
4. 服务端重新验证真实 MIME、尺寸、大小及解码结果，不信任扩展名和客户端检查。
5. 识别类别、主色、图案、版型；不确定时返回 unknown，不猜测品牌、身材或价格。
6. 用户可以改标签；点击确认后，照片与标签在同一存储事务中写入衣柜。
7. 保存成功才提示“已收录”。保存失败保留草稿，可继续本次搭配，但明确尚未入库。

已有衣物可直接从衣柜选择，不再次上传识别。补录裤子、鞋子使用相同收录流程，但不自动启动以上衣为起点的推荐。

### 5.2 重复检测

- 对标准化图片内容计算摘要；同一图片的重复保存请求复用已有条目。
- 用类别、主色、图案和版型寻找疑似重复候选，让用户选择“使用已有”或“另一件，继续收录”。
- 同色同款不等于同一件，不自动合并或覆盖。
- 拍摄角度、光照和编码改变会影响摘要，因此不承诺重拍也能精确识别。
- 每次保存操作分配稳定 operationId，重复点击和重试不能插入第二份。

### 5.3 推荐与已有衣物匹配

1. 用户选择日常休闲、轻松通勤或周末约会。
2. 本地按类别等条件筛选有限数量的裤子、鞋子候选；仅发送必要标签及候选 ID，不发送整柜照片。
3. 模型返回一套结构化建议：裤子类别、颜色、版型、长度倾向；鞋子类型、颜色；理由与选用候选 ID。
4. 服务端校验字段、类别及 ID 是否属于本次提交的候选；客户端再次按当前衣柜确认关联，避免删除后的旧条目被标记为已有。
5. 精确标签匹配展示“衣柜已有”；近似候选展示差异与“衣柜有相似款”；不存在时展示“衣柜暂未找到匹配款”。
6. 用户若选择近似候选，先更新本套方案及其快照，再生成图片，避免文字推荐与所选实物不一致。
7. 换一套按裤型、颜色和鞋型组合去重；有界重试仍无新方案时提示调整场景，不无限调用。

“衣柜已有”仅说明关联了当前已保存的实物条目，不表示生成图中的精确商品属于用户。

### 5.4 整套 AI 示意图

每套有效文字建议展示后，自动提交一次整套图任务；重绘需要明确操作，不能因页面重渲染重复触发。

输入：
- 已确认的推荐结构和场景。
- 用户选定上衣的压缩参考照片；需要体现已有裤子或鞋子时，可发送实际选用的单品照片。
- 仅发送本套需要的图片，并在首次生成前说明图片会进入图像服务处理。

输出：
- 一张无人物的衣物组合图，包含上衣、裤子和鞋子。
- 默认采用平铺／单品组合构图，不要求模型在图中写文字，标签由页面显示。
- 尽量保留上衣的颜色、图案和轮廓，但生成可能改变细节，界面明确提示“AI 搭配示意，非实物或试穿保证”。
- 图片与标签明显不符时允许反馈和重绘，保留原照片卡片作为真实依据。

缺少参考图输入能力的模型不能承诺保留用户上衣外观。真实模型选型需通过样本验证；纯文字想象图只能明确作为风格参考，不能冒充用户同一件衣服的复现。

### 5.5 异步任务、缓存与重试

状态：queued → running → succeeded；另有 failed、expired、cancelled。

- POST 返回 202 与不透明 jobId；浏览器通过查询接口获取状态。
- 应用持久记录 jobId、匿名会话归属、requestHash、供应商任务 ID、状态、过期时间和错误码。
- jobId 不作为唯一授权凭证；查询、下载和取消均校验会话归属。
- 任务缓存键包含输入图片摘要、确认标签、候选选择、场景、模型与提示版本；缓存必须按会话隔离，不跨用户复用私人图片。
- 幂等键与请求摘要绑定，同键不同内容拒绝；同一次网络重试只创建一个计费任务。
- 请求超时后先查询已有任务，不直接再生成一张；结果未知时先对账，不能盲目重试计费操作。
- 轮询逐步退避，页面隐藏时暂停高频查询；刷新后通过本地 jobId 恢复。
- 更换起点或修改场景后递增请求版本，旧响应不能覆盖新页面。
- 图片失败仍显示文字和真实单品卡片，提供单独重试。

优先选支持原生异步任务、查询和参考图输入的图像服务。如果供应商只有同步接口，需要独立 worker 加持久队列执行；不得在 Route Handler 返回后留下未等待的 Promise，也不得依赖函数内存或临时文件保存任务。
任务元数据的具体持久服务随部署地区确定，这是运行可靠性的实施依赖，并不等于开启用户云衣柜。

## 6. 数据模型

IndexedDB 建议包含以下对象存储：

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| garments | id、imageId、imageHash、category、type、color、pattern、fit、source、revision、createdAt、updatedAt | source 区分用户实物和示例，不允许生成图冒充实物 |
| images | id、Blob、mime、width、height、origin、createdAt | 图片与条目通过事务一致保存 |
| outfitSnapshots | id、起点快照、推荐字段、选中条目 ID、场景、模型／提示版本、generatedImageId | 历史内容不可因后续推荐变化而改写 |
| favorites | id、outfitId、createdAt | 同一方案不重复收藏 |
| pendingJobs | jobId、requestVersion、outfitId、expiresAt | 不包含供应商密钥 |
| meta | schemaVersion、迁移记录、设置 | 迁移失败不清空旧数据 |

- 图片用 Blob，不用大体积 Base64 JSON 作为正式存储。
- 收藏时将生成图下载保存为本地 Blob，不只存会过期的远程链接。
- 如果收藏先保存文字，图片完成后事务性补全；失败时说明“文字已保存，图片未保存”。
- 删除衣物不删除已有收藏快照；已有标识按当前衣柜动态计算。
- 清空全部数据同时删除衣柜、收藏与无引用图片；操作前确认且解释不可恢复。
- 本地存储可能被清理、配额回收或浏览器重置，不承诺永久保存。可申请持久存储，但不能假定一定获准。
- 首版不把衣柜自动上传云端；跨域或跨设备不共享 IndexedDB。

## 7. 服务接口草案

以下是目标契约，不是已存在的接口。

| 接口 | 输入／用途 | 正常结果 |
| --- | --- | --- |
| POST /api/session | 创建受控试用的匿名会话 | 设置签名的 Secure、HttpOnly Cookie |
| POST /api/garments/analyze | 压缩照片＋requestId | 可编辑识别标签 |
| POST /api/outfits/recommend | 已确认起点＋场景＋有限候选＋去重信息 | 完整结构化推荐 |
| POST /api/outfits/image-jobs | 已确认方案＋参考图＋Idempotency-Key | 202、jobId、expiresAt |
| GET /api/outfits/image-jobs/:id | 查询本会话任务 | 状态、进度阶段或错误码 |
| GET /api/outfits/image-jobs/:id/image | 获取已完成图片 | 验证权限后返回图片流 |
| DELETE /api/outfits/image-jobs/:id | 尽力取消并标记不再需要 | 不保证供应商可取消或退款 |

错误返回统一包含 code、用户可读 message、requestId 和 retryable。区分输入错误、额度不足、限流、超时、供应商不可用、任务过期及无权访问。
外部图片地址不由客户端任意指定给服务端抓取；下载仅接受受信任任务结果，限制域名、重定向、大小与超时，避免 SSRF。
AI 输出作为不可信数据处理，不执行模型返回的代码、HTML、链接或额外指令。

## 8. 隐私、安全与费用

- AI 密钥仅放服务端 secret，不写入 NEXT_PUBLIC_*、GitHub、前端 bundle、日志或浏览器存储。
- 生产环境启用 HTTPS；同源 API 校验 Origin 和会话，写操作防 CSRF。
- 私人接口和图片响应使用 private/no-store，不进入共享缓存或 Service Worker 的自动缓存。
- 日志只记录任务 ID、错误类别、耗时和计费统计，不记录原图、完整提示内容或个人照片 URL。
- 临时参考图和生成结果采用短期保留：目标为任务终止后 24 小时内清理；具体时限必须与供应商能力和部署配置一起验证并展示。
- 供应商的训练使用、保留期限和处理地区单独核实；应用删除不等于供应商已立即删除，不能承诺未经核实的零留存。
- 服务端限制文件大小、像素数、请求频率、并发和全局预算；并发下原子预留额度，失败或结束后核算。
- 匿名试用采用每会话额度＋网络层限流＋全局费用硬上限。重新获取 Cookie 不能被视为可靠身份验证。
- 初期可用受控访问的试用站点；向公众开放前增加滥用防护。仅禁用前端按钮不构成安全限流。
- 识别、文字、图片生成分别统计成本。每次最多一套图，优先复用本会话已成功结果；不自动生成多张候选图。

预算、每人额度、任务超时和保留时限均为上线前配置项，需用户确认；本文不购买服务或授权持续支出。

## 9. PWA 与移动端体验

- 优先手机相册与拍照入口，设备权限失败时保留相册上传。
- Manifest、应用图标、独立窗口展示和安装说明需要实际实现；不假定所有浏览器都支持同样安装方式。
- Service Worker 只缓存应用外壳和明确允许的静态资源；本地照片从 IndexedDB 读取。
- 首次访问需联网；离线可查看已保存衣柜和收藏，可手动录入；真实 AI 分析、推荐和生成需联网。
- 静态资源带版本，更新提示不能中断待保存草稿；先完成存储迁移再切换数据版本。
- 360px 手机布局和桌面布局都要验证；控件主要触摸区域至少 44px，支持键盘、焦点和可读错误。
- 已知 Demo 曾出现推荐区域空白的反馈，正式版须增加内容可见性回归测试，不能只断言 DOM 中存在文本。

PWA 的安装和缓存需分别实现及验证，参考 [Next.js PWA 指南](https://nextjs.org/docs/app/guides/progressive-web-apps)。

## 10. 项目结构与部署

建议在现有仓库保留以下边界：

- docs/：产品设计、技术方案、后续接口与验证记录。
- demo/：已有模拟原型，保留可追溯版本。
- web/src/app/：页面、布局与 api/ Route Handlers。
- web/src/components/：衣物卡片、确认表单、结果、任务状态等组件。
- web/src/lib/domain/：标签规则、匹配、去重、快照等纯业务逻辑。
- web/src/lib/storage/：IndexedDB、事务与数据迁移。
- web/src/lib/ai/：mock／real 供应商适配器及共享契约。
- web/src/lib/server/：会话、任务存储、限流、额度和供应商调用。
- web/tests/：单元、组件、接口与端到端测试。

服务端模块不可被客户端组件导入。首版不加入微服务、向量数据库、复杂全局状态库或单独 Python 后端。
构建系统使用单一包管理器和锁文件；CI 按锁文件安装，不跳过依赖安全检查。若本机安装环境受阻，修复环境后再实施，不能把绕过依赖策略作为解决方案。

当前 Demo 是静态托管。正式版新增 Route Handlers 后不能沿用“只有静态文件”的部署方式；需要 Next.js 兼容运行环境，或将 API 独立托管并明确同源代理和安全边界。
是否继续使用现有托管平台，需验证运行时、框架适配、请求时限、任务持久化、秘密管理和目标地区访问，不默认直接搬运构建产物。

部署分开发／预览／正式环境，使用不同密钥和额度。先小范围试用；代码可回滚，IndexedDB 迁移需独立设计回滚或向前兼容，回滚代码不应清空用户衣柜。

## 11. 后续云同步与手机 App

当用户明确要求跨设备衣柜时，再加入登录、云数据库与对象存储。候选方案是 Supabase Auth + PostgreSQL + Storage，并配置用户级访问隔离及私有图片权限。[Supabase 存储权限指南](https://supabase.com/docs/guides/storage/security/access-control)

云迁移必须经用户确认后上传本地数据，定义稳定 ID、版本冲突和删除同步规则，不能登录后静默上传整柜照片。
国内／海外用户分布与服务可用性需先验证，再确定云服务商。
需要上架手机应用时，可评估 Capacitor 复用 Web UI；服务端接口继续部署在服务器，不把密钥或 Next.js 服务端逻辑打包到手机。Electron 仍不是手机端替代品。

## 12. 分阶段实施

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| M0：基础验证 | 确定服务地区与预算；验证模型参考图、结构化输出、异步能力及部署环境 | 能用授权样本跑通一套真实推荐和图像任务；记录成本、延迟与限制 |
| M1：本地闭环 | React/Next.js 页面、IndexedDB、上传确认、收录、去重、衣柜及收藏 | 不依赖 AI 也能验证本地操作，模拟模式明确标识 |
| M2：真实推荐 | 识别适配器、标签校正、场景、结构化推荐和已有匹配 | 空衣柜可推荐，已录入候选正确关联，失败可解释 |
| M3：整套示意图 | 异步任务、参考图、状态恢复、缓存、重试及限额 | 实际生成上衣＋裤子＋鞋子示意图，图失败不阻断文字 |
| M4：交付加固 | PWA、真机、可访问性、安全、费用及数据迁移测试 | 必需测试通过，实测结果与限制可核查，发布可回滚 |

不先开发账号、支付或云衣柜，也不把“换个框架”当成 MVP 完成。
M0 的服务商、地区、实际型号和预算是待决事项；本方案已确定架构和接口边界，但没有假装这些外部依赖已接通。
